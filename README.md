# QAR (Quick Access Recorder) Telemetry Storage & Analysis System

Прототип специализированной системы для приёма, хранения и анализа телеметрии полёта самолёта, ориентированной на высокоскоростную запись данных в формате, используемом в QAR-системах.

Проект разрабатывается в рамках выпускной квалификационной работы (ВКР).

---

## 📌 Описание проекта

Данный проект представляет собой программную систему, предназначенную для работы с телеметрией полёта, поступающей от бортового устройства сбора данных (**FDAU**). Структура телеметрии задаётся **Frame Layout Table**, используемой в стандартах **ARINC**, и описывает набор параметров, их расположение в кадрах и частоту дискретизации.

Телеметрия полёта — это поток высокочастотных числовых данных, включающий сотни параметров (скорость, высота, конфигурация механизации крыла, параметры двигателей и т.д.), поступающих непрерывно в течение всего полёта. Основная сложность при работе с такими данными заключается в их эффективной записи на диск: данные поступают быстро, имеют временную привязку и создают высокую нагрузку на подсистему ввода-вывода.

Цель проекта — разработка собственного ядра хранения данных, оптимизированного под подобные сценарии, и демонстрация его применимости на примере телеметрии QAR.

---

## 🎯 Цели и задачи

**Основная цель:**
Создание прототипа системы хранения и анализа полётной телеметрии, обеспечивающей устойчивую и эффективную запись высокочастотных данных на диск.

**Задачи проекта:**

- приём потока телеметрии от эмулируемого FDAU;
- буферизация входных данных в оперативной памяти;
- реализация механизма записи на диск на основе **LSM-деревьев**;
- уплотнение данных (compaction) и сокращение числа операций ввода-вывода;
- реализация чтения по временным диапазонам и параметрам;
- реализация базовой аналитики и CSV export для дальнейшей обработки.

---

## 🧠 Архитектура (обзор)

Система состоит из следующих логических компонентов:

1. **Источник данных (FDAU Emulator)**
   Генерирует поток телеметрии в соответствии с Frame Layout Table.

2. **Ingest-модуль**
   Принимает и группирует входные данные, формируя записи для ядра хранения.

3. **Storage Core (LSM-based)**
   - in-memory memtable;
   - запись упорядоченных SSTable-файлов на диск;
   - manifest для списка активных SSTable;
   - recovery после штатного завершения;
   - базовый механизм compaction;
   - оптимизация под временные ряды.

4. **Disk Layer**
   Хранение упорядоченных SSTable-файлов с блочной структурой и metadata для
   пропуска нерелевантных блоков при чтении. Продвинутое сжатие и дополнительные
   форматы хранения остаются направлением дальнейшего развития.

5. **Analysis Module**
   Минимальный интерфейс для чтения, агрегатов `count`, `min`, `max`, `avg` и
   CSV export.

## 📊 Анализ данных

На этапе MVP модуль анализа поддерживает:

- выборку данных по диапазону времени;
- выборку по набору параметров;
- простые агрегатные операции (min / max / avg);
- экспорт результатов в удобные форматы (например, CSV).

Полноценная поддержка SQL не является целью MVP и может быть добавлена на более поздних этапах.

### Быстрый старт

Синхронизация окружения и dev-зависимостей через `uv`:

```powershell
uv sync --all-groups
```

Команды ниже запускаются через `uv run`, поэтому активировать `.venv` вручную не
требуется.

Запуск ingest с реальным `StorageCore` и периодическим выводом статистики:

```powershell
uv run python src/main.py ingest --duration 10 --print-stats
```

Чтение сохранённых точек за полуинтервал `[start_ts_ns, end_ts_ns)`:

```powershell
uv run python src/main.py query --start-ts-ns 0 --end-ts-ns 1000000
```

Расчёт агрегатов `count`, `min`, `max`, `avg` за тот же полуинтервал:

```powershell
uv run python src/main.py aggregate --start-ts-ns 0 --end-ts-ns 1000000
```

Фильтр по параметрам задаётся через `--parameter-ids`:

```powershell
uv run python src/main.py query --start-ts-ns 0 --end-ts-ns 1000000 --parameter-ids 1,2,3
uv run python src/main.py aggregate --start-ts-ns 0 --end-ts-ns 1000000 --parameter-ids 1,2,3
```

CSV export доступен для точек и агрегатов:

```powershell
uv run python src/main.py query --start-ts-ns 0 --end-ts-ns 1000000 --output-csv out/points.csv
uv run python src/main.py aggregate --start-ts-ns 0 --end-ts-ns 1000000 --parameter-ids 1,2,3 --output-csv out/aggregates.csv
```

Benchmark harness:

```powershell
uv run python src/main.py benchmark
uv run python src/main.py benchmark-scale
```

Проверки проекта:

uv run ruff check . --fix

### Python API MVP

```python
from core.storage import (
    StorageCore,
    points_to_rows,
    write_aggregates_csv,
    write_points_csv,
)
from settings import settings

storage = StorageCore(settings=settings)
try:
    points = storage.query_range(0, 1_000_000, {1, 2, 3})
    rows = points_to_rows(points)
    write_points_csv(points, "out/points.csv")

    aggregates = storage.aggregate_range(0, 1_000_000, {1, 2, 3})
    write_aggregates_csv(aggregates, "out/aggregates.csv")
finally:
    storage.close()
```

Семантика API:

- временной диапазон всегда задаётся полуинтервалом `[start_ts_ns, end_ts_ns)`;
- `parameter_ids=None` означает чтение или агрегацию без фильтра по параметрам;
- результаты чтения отсортированы по `timestamp_ns`, затем `parameter_id`;
- агрегаты возвращаются по `parameter_id`;
- CSV точки имеют колонки `timestamp_ns`, `parameter_id`, `value`;
- CSV агрегаты имеют колонки `start_ts_ns`, `end_ts_ns`, `parameter_id`,
  `count`, `min`, `max`, `avg`.

### Durability MVP

- При штатном `StorageCore.close()` текущая memtable сбрасывается в SSTable.
- Durable считаются данные, записанные в SSTable и отражённые в manifest после
  успешного сохранения manifest.
- Данные, оставшиеся только в memtable, могут быть потеряны при аварийном
  завершении процесса до flush.
- WAL и полная crash-safety для несброшенной memtable не реализованы и не входят
  в MVP/v2.

## ⚙️ Технологии

- **Язык реализации:** Python
- **Архитектурный подход:** Log-Structured Merge Tree (LSM)
- **Формат данных:** временные ряды (time-series)
- **Хранение:** memtable, SSTable, manifest, recovery, compaction
- **Расширяемость:** возможность переноса ядра на **Rust** в дальнейшем

Готовые библиотеки используются для вспомогательных задач и инфраструктуры, в то время как ядро хранения разрабатывается самостоятельно.
